# Orizon Nimasa

**Source-labelled ocean and coastal conditions for Nigeria's coast.**

Orizon Nimasa is a mobile-friendly web app that puts marine and weather readings for the Lagos coast on one dashboard. Every value shows what it is (observed, forecast, model estimate or derived), where it came from, and how old it is. The app also generates rule-based advisories and has a staff console for monitoring data feeds.

It is an **informational tool**. It is not an official forecast, warning, navigation aid or emergency service, and it does not guarantee safe travel or fishing outcomes.

> **Status: pilot MVP front-end.** By default the app runs on **synthetic sample data** generated in the browser (`src/api/mockApi.ts`). No real data source is approved or connected yet. Alert thresholds are illustrative placeholders. See [Known limitations](#known-limitations).

Built with React 18, TypeScript, Vite, React Router, and Leaflet (OpenStreetMap tiles). Tests use Vitest. The product name is Orizon Nimasa, but the npm package is still called `blueintel-nigeria`.

## What the app does

### The four design rules

Every screen follows the same rules, which is what makes the app different from a generic weather dashboard:

1. **A source on every value.** Each number names its provider and dataset, and links to licence and attribution details.
2. **Time you can check.** Source timestamps are shown in WAT (Africa/Lagos, UTC+1). Data older than its freshness limit is labelled **Stale** and is never presented as current.
3. **Observed is not forecast.** Four badges keep the data types separate: *Observed*, *Forecast*, *Model estimate*, *Derived*.
4. **Gaps stay visible.** Missing readings show as breaks in the chart and as "Missing" in the table. Nothing is interpolated or invented.

### What you can see and do

**Public website** (`/`, `/about`, `/feedback`)
- **Landing page:** a live snapshot of the five indicators for the selected location, the four rules above, the candidate data sources, and a "what this tool is not" notice.
- **About & limits:** product principles, what the tool does not do, and the privacy position (no account, no personal data collected).
- **Pilot feedback:** a short optional form (found what you needed? was the source and time clear? free-text comments).

**Public dashboard** (`/dashboard`, `/alerts`, `/sources`, `/insights`)
- **Dashboard**
  - **Latest values** for five indicators: wave height, wind speed, sea surface temperature, visibility and current speed. Each has a type badge and a freshness badge.
  - **Map room:** an interactive Leaflet map with one colour-coded layer per indicator, a legend, and a dashed box showing the MVP coverage area. Pick a location from a marker or a chip.
  - **Trend chart** for any indicator, with 24 h / 48 h / 7 day ranges. Forecast values are styled differently, gaps are visible, and the illustrative alert threshold is drawn as a line. A "view as a table" option is provided as an accessible alternative.
  - **3-day outlook** (daily maximum wave height and wind) and a **plain-language summary** generated by a fixed rule, not by AI.
  - **Export** the chart as CSV, PDF (chart report), PNG or JPG. Exports carry the source, units and timestamps.
- **Alerts:** location-based advisories, filterable by location and by type (*Coastal conditions*, *Ocean navigation*, *Waterway navigation*). Each alert shows the trigger, data type, source, source time, issue time and validity window. The full rule table is shown below the list.
- **Data sources:** the sources in use, candidate providers (with licence and attribution status), the datasets with their expected refresh and stale-after limits, and a source investigation checklist.
- **AI insights:** a *disabled* placeholder showing the planned guardrails. No AI feature is active in this release.

A red **alert ticker** runs across the dashboard and also reports data-quality problems (stale feeds, service unavailable, no data yet).

**Staff operations console** (`/admin/login`, `/admin`)
- Application health and data-feed health, reported separately.
- Feed freshness per location and dataset.
- Recent ingestion runs (source, outcome, records accepted and rejected, error category).
- Alert rule configuration (read-only in the UI) and an audit trail.
- In demo mode only: a **feed simulator** (Normal / Stale feed / Service error) to review how the UI behaves when data goes bad. It resets when you leave the console so it never leaks into the public dashboard.
- In live mode only: a **Run ingestion now** button.

The app is also installable as a PWA-style home-screen app (web manifest, starts at `/dashboard`).

### Coverage and indicators

**Coverage area:** Lagos coast (a placeholder until the pilot area is confirmed). Eight locations in three zones:

| Zone | Locations |
|---|---|
| Coastal | Badagry, Lagos Harbour (Apapa), Bar Beach (Victoria Island), Lekki, Eleko |
| Waterway | Lagos Lagoon, Badagry Creek |
| Offshore | Lagos Offshore Approach |

**Indicators:**

| Indicator | Unit | Data type | Fresh for | Forecast |
|---|---|---|---|---|
| Wave height | m | Model estimate | 3 h | Yes |
| Wind speed | km/h | Observed | 2 h | Yes |
| Sea surface temperature | °C | Model estimate | 12 h | No |
| Visibility | km | Model estimate | 3 h | Yes |
| Current speed | km/h | Model estimate | 3 h | Yes |

Each dataset has its own stale-after limit based on how often it is expected to update, not one universal threshold. These are defined in `src/config.ts`.

### How alerts work

There are 9 rules (`ALERT_RULES` in `src/config.ts`) across the three categories. The logic lives in `src/lib/alerts.ts` and is covered by unit tests:

- A rule compares the latest **valid, non-forecast** value against a threshold (`>=` or `<=`, inclusive).
- **Missing values and forecast points never trigger an alert.**
- **Duplicate suppression:** a repeat trigger inside the rule's suppression window (3 to 6 h) does not create a new alert.
- **Validity window:** each alert is valid for a set time, then shows as *Expired*.
- **Stale suppression:** if the feed is stale, the alert is shown as "Not current: data stale" rather than Active, and the dashboard's advisory tile says "Not assessed".
- Rules can be limited to zones (for example, small-craft wind and visibility rules apply only to waterways).

In demo mode the browser evaluates the rules. In live mode the server evaluates them and the UI displays the result.

## Quick start

Requires Node.js 18 or newer.

```bash
npm install
npm run dev        # http://localhost:5173 (Vite picks the next free port if busy)
npm test           # 15 unit tests: freshness policy + alert rules
npm run build      # type-check, then production build into dist/
npm run preview    # serve the production build locally
```

To pin the dev port: `npm run dev -- --port 5133`.

### Demo mode vs live mode

The app picks its data source from one environment variable, `VITE_API_BASE_URL`:

| `VITE_API_BASE_URL` | Mode | Data | Admin sign-in |
|---|---|---|---|
| **empty / unset** | Demo | Synthetic, generated in the browser | UI stub: any details sign in |
| **set** (e.g. `http://127.0.0.1:8015/api/v1`) | Live | From the FastAPI backend | Real: bearer token from the API |

> **Heads up:** the committed `.env.example` and `.env.local` both **set** `VITE_API_BASE_URL` to `http://127.0.0.1:8015/api/v1`. If you copy `.env.example` to `.env` (or keep `.env.local`) without a backend running, the app starts in live mode and shows "Data service unavailable". **To run the standalone demo, make sure `VITE_API_BASE_URL` is blank.**

Environment variables (see `.env.example`):

| Variable | Purpose |
|---|---|
| `VITE_API_BASE_URL` | Backend base URL. Empty means demo mode. Set to `/api/v1` to go through the Vite dev proxy. |
| `VITE_API_PROXY` | Proxy target when using `/api/v1` (default `http://127.0.0.1:8015`). |
| `VITE_TILE_URL` | Basemap tile URL (default: public OpenStreetMap server). |
| `VITE_TILE_ATTRIBUTION` | Attribution text shown under the map and in the footer. |

No secrets belong in this client. Provider API keys live on the backend only.

## Connecting real data

1. **Choose one approved source** whose licence, coverage and attribution have been reviewed (see the candidates on the *Data sources* page), and build its ingestion adapter on the server.
2. **Run the FastAPI backend** and set `VITE_API_BASE_URL`. `src/api/client.ts` adapts the API's snake_case/ISO responses to the shapes the UI uses. Either:
   - set the variable to the full API URL and add this front-end's origin to the API's `CORS_ORIGINS` (restart the API afterwards), or
   - set it to `/api/v1` and let Vite proxy `/api` to `http://127.0.0.1:8015` (override with `VITE_API_PROXY`).
3. **Update the config** in `src/config.ts`: `SOURCES`, `DATASETS`, `LOCATIONS` and `ALERT_RULES`. Location coordinates for the two waterways are approximate and should come from `GET /locations`.
4. **Get thresholds reviewed** by a marine or meteorological specialist before any pilot. The current values are placeholders.
5. **Move alert evaluation to the server** for production (the UI already displays server-evaluated alerts when the API provides them).

In live mode the app polls the API every 5 minutes.

### Backend endpoints the client calls

Base path `/api/v1`.

| Area | Endpoints |
|---|---|
| Data | `GET /locations`, `/datasets`, `/sources`, `/series`, `/summaries`, `/locations/{id}/summary` |
| Alerts | `GET /alerts`, `/alert-rules` |
| Export | `GET /locations/{id}/series.{csv,png,jpg,pdf}` (server-built chart files) |
| Feedback | `POST /feedback` |
| Health | `GET /health` |
| Admin (bearer token) | `POST /admin/auth/login`, `GET /admin/auth/me`, `GET /admin/feeds`, `/admin/alert-rules`, `/admin/audit-log`, `/admin/ingestion-runs`, `POST /admin/ingestion/run` |

`client.ts` also wraps further admin endpoints (rule/source/dataset updates, staff management, feedback review, password change) and the planned `POST /insights/query`. **The UI does not use these yet.**

## Known limitations

- **All data is synthetic by default.** Several screens hard-code "sample data" wording (landing snapshot, dashboard source line, footer). This text will need to become dynamic once real sources are connected.
- **Alert thresholds are illustrative.** Each rule is marked "Domain review pending".
- **Demo admin sign-in has no real authentication.** Live-mode sign-in is real, but the token is kept in `sessionStorage` for the tab, and role-based authorisation must be enforced by the server.
- **The admin console is mostly read-only.** Rule thresholds, sources and staff cannot be edited from the UI yet.
- **AI insights are not implemented.** The page is a disabled placeholder.
- **Coverage area, location list and the five indicators are assumptions.** The product requirements leave both open for pilot discovery.
- **English only.** Language support will follow discovery.
- **Basemap:** the public OpenStreetMap tile server has usage limits. Choose a tile provider before launch.
- **Privacy:** the public site collects no personal data, but a full privacy notice and a Nigerian data-protection review are required before production.

## Deployment

`npm run build` produces a static site in `dist/`. Configure your host with an **SPA fallback** so deep links such as `/alerts` and `/admin` serve `index.html`. Set the `VITE_*` variables at build time, since Vite inlines them.

## Project structure

```
src/
  App.tsx             route table (public site, dashboard, admin login, admin)
  config.ts           locations, datasets, sources, alert rules, labels, map bounds
  types.ts            shared types (Series, Point, AlertRule, AlertEvent, ...)
  api/
    mockApi.ts        synthetic data generator (demo mode)
    client.ts         real FastAPI client + response adapters (live mode)
  context/
    DataContext.tsx   fetches data, computes freshness and alerts, polls in live mode
    AuthContext.tsx   admin sign-in (stub in demo mode, token-based in live mode)
  layouts/            PublicLayout (website), DashboardLayout (sidebar), AdminLayout
  pages/              Landing, About, Feedback, Home (dashboard), Alerts, Sources,
                      Insights, AdminLogin, Admin (+ AdminLive for live mode)
  components/         MapView, TrendChart, AlertTicker, Sidebar, Topbar, Footer,
                      Badges (type/freshness), States (loading/empty/error)
  lib/                freshness, alerts, csv, export (PNG/JPG/PDF), time
  __tests__/          Vitest tests for freshness and alert rules
public/               icons and web manifest
```
